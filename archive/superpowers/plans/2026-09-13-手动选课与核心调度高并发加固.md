# 官网同款手动报名退选与高并发核心加固深度实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 
1. 落地至道教务官网同款选课交互：支持手动报名、退选（二次确认）、退选后无冷却立即重选，严格复刻官方 `btn_type` + `can_select` + `title` 状态机与全量刷新机制；
2. 建立手动写操作与调度器自动抢课引擎的双向同步机制：`MarkDone`/`RemoveDone` 状态协同、单账号单课程并发提交互斥锁、数据持久化入库；
3. 同步根治 4 项严重影响并发选课的核心 CRITICAL 缺陷：
   - 调度器 C1：解除满员不再受 40s 老快照卡死，退选空位黄金期秒抢；
   - 调度器 C2/C3：重登退避拆分独立时间戳与上限封顶，根治 token 失效永久冻结；
   - 验证码 C1：消除 `SetCaptchaConcurrency` 信号量死锁与数据竞态；
   - 前端 C1：根除管理员查看学生账号时 401 误杀 Admin 会话引发白屏的漏洞。

**Architecture:**
- **后端**：
  - 新增 `POST /api/electives/select` 与 `POST /api/electives/select/exit` 接口，鉴权继承 `sessionAccount(r)`，下沉调用 `zhidao.Client.SelectClass` / `ExitClass`；
  - 调度器暴露带锁协同接口 `MarkDone`（写 success + task_log + 内存 done）、`RemoveDone`（清内存 done + 写 task_log exit，唤醒自动重抢）、`RemoveFull`；
  - 引入 per-account×class 的轻量互斥（复用/增强 `inflight` 判定），杜绝手动与自动 goroutine 产生重复提交触发平台熔断；
  - 重构 `releaseFullIfFreedLocked`：只要快照有余量（`selected_count < max_count`），立即解除 `full` 标记；
  - 重构 `maybeRelogin`：拆分 30s 冷却与指数退避，增加 5 次（10 分钟）退避封顶，成功时清零。
- **前端**：
  - `Select.tsx` 依照逆向契约渲染：`btn_type=1` 渲染红色退选按钮，`btn_type=2` 渲染报名按钮，禁用状态由 `can_select` 与开窗状态联合控制，悬浮展示 `title` 禁用文案；
  - 点击退选弹出极简黑白二次确认 Modal（复刻官网 `layer.confirm`）；
  - 操作成功/失败后立即触发 `invalidateQueries(['electives'])` 执行全量重拉，开窗状态下自动提速轮询至 2 秒。

## 阶段一：调度器与验证码 CRITICAL 缺陷根治

### Task 1: 修复调度器满员解封阻断与重登退避冻结 (CRITICAL C1, C2, C3)

**Files:**
- Modify: `backend/internal/scheduler/scheduler.go`
- Test: `backend/internal/scheduler/scheduler_test.go`

**Context / Root Cause:**
1. `releaseFullIfFreedLocked`（scheduler.go:981）在快照时间 `> snapshotTTL (40s)` 时直接 return，导致在 30s 探测节流期或快照稍老时，即使有人退选释放了名额，也永远无法解除 full，错失 250ms 冲刺捡漏；
2. `reloginAt` 被 30s 探测节流和指数退避两套逻辑复用，且 `reloginFail` 无上限累加（位移溢出风险），导致外部服务故障时自动重登永久冻结。

- [ ] **Step 1: 编写测试用例重现缺陷**

在 `backend/internal/scheduler/scheduler_test.go` 中添加：
1. `TestReleaseFullIfFreedEvenIfSnapshotOld`：构造标记为 full 的课程，提供一份时间戳超过 40s 但 `selected_count < max_count` 的快照，调用 `releaseFullIfFreedLocked`，断言 full 状态被成功解除；
2. `TestReloginBackoffCappedAndReset`：构造重登连续失败，断言退避时间封顶不超过 10 分钟；模拟重登成功，断言 `reloginFail` 计数被清零。

- [ ] **Step 2: 运行测试验证失败**

预期：FAIL。

- [ ] **Step 3: 实施修复代码**

修改 `backend/internal/scheduler/scheduler.go`：
1. `releaseFullIfFreedLocked`：移除 `time.Since(s.acctDataAt[acct]) > snapshotTTL` 的绝对阻断条件；只要快照中该课程数据存在且 `selected_count < max_count`，立即 `delete(s.full[acct], classID)`；
2. `maybeRelogin` 与 `reloginFail`：
   - 增加失败计数上限 `const maxReloginFail = 5`（$30s \times 2^5 = 960s$，封顶 10 分钟）；
   - 在重登成功分支明确重置 `s.reloginFail[acct] = 0`；
   - 保证 `reloginCooldown` 与 `reloginBackoff` 逻辑分离清晰。

- [ ] **Step 4: 运行回归测试**

运行：`cd backend && go test -v ./internal/scheduler -run "TestReleaseFullIfFreedEvenIfSnapshotOld|TestReloginBackoffCappedAndReset"`
