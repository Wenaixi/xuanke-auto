## 二、发现的真实缺陷（按严重度分级）

### 🔴 CRITICAL

**C1. 管理员账号名比较硬编码 "admin"，改名后删除保护失效**
- 位置：`backend/internal/api/handler.go:678`（`handleAdminDeleteAccount`）
- 详情：`if ... req.Account == "admin"` 只挡字面量 "admin"。`AdminNameValue()` 支持 `XUANKE_ADMIN_NAME` 改名后，管理员可删除改名的管理员账号记录，引发凭据误删。应与 `d.AdminNameValue()` 判等。
- 核实结论：**实锤**。其余 handler 已统一用 `d.AdminNameValue()`，此处是唯一残留字面量。

**C2. 学生账号名为 "admin" 时可穿透 `?account=` 代理操作任意账号（水平越权）**
- 位置：`backend/internal/api/handler.go` 的 `handleElectives`/`handleElectiveSelect`/`handleElectiveExit`/`handleSetTargets`/`handleState`（穿透判定均为 `acct == d.AdminNameValue()` 字符串相等）
- 详情：`?account=` 穿透能力只校验"会话绑定的账号名是否叫 admin"，不校验 `Sessions.IsAdmin(tok)`（Admin:true）。若存在/注册了名为 `admin` 的学生账号（同名账号在教务系统常见），该账号会话即可读任意账号课程、改目标、代报名/退选——水平越权链完整成立。
- 核实结论：**实锤**。需新增 `Sessions.IsAdmin(tok)` 判定并替换所有穿透点的字符串比较（登录入口 `handleLogin` 先比对管理口令失败即 return，不短路教务登录，本身安全）。

### 🟠 MAJOR

**M1. spawnChain 缺少 inflight 去重——手动在飞 + 自动链并发双发包（CLAUDE.md 声称已修但代码没有）**
- 位置：`backend/internal/scheduler/scheduler.go:822-825`
- 详情：`spawnChain` 在 `SelectClass` 前直接 `s.inflight[acct][t.ClassID] = true` 覆盖写入，前方无 `inflightHas` 检查。`inflightHas()`（scheduler.go:1037）全工程无调用点。链级去重是 `chainMu`（key=acct+publishID），与手动 `TryAcquireSubmit` 级 inflight 锁不相交。实际序列：手动报名课程 X（inflight[X]=true）→ 300ms 后调度器 tick → spawnChain 不检查 inflight 直接发第二包 → 真双包并发打平台。
- 核实结论：**实锤**。grep `inflightHas` 仅命中定义行（scheduler.go:1037），`spawnChain`（825 行）确实无检查。修复：`spawnChain` 前置 `if s.inflightHas(acct, t.ClassID) { continue }`。

**M2. `ProbeNow` 对 `lastProbe/lastData/lastDataAt` 三字段无锁写——生产路径数据竞态**
- 位置：`backend/internal/scheduler/scheduler.go:516-518`
- 详情：`ProbeNow` 由 `/api/electives` HTTP handler 调用，三字段无锁写入；同文件 `tick()`/`probe()`/`ElectivesSnapshot`/`ElectivesSnapshotFor` 均锁内读写。300ms tick goroutine + HTTP handler goroutine 必然重叠。`ProbeForAccount`（449-460）展示了正确模式（网络锁外、字段写锁内），ProbeNow 是遗漏。
- 核实结论：**实锤**。-race 未覆盖 handler↔tick 生产路径，但代码静态明确。修复：字段写包进 `s.mu.Lock()`。

**M3. release.yml Windows 打包 `mkdir -p` 在 pwsh 下必挂（release 从未实跑过）**
- 位置：`.github/workflows/release.yml:92`
- 详情：`mkdir -p ../dist-artifacts` 是 POSIX 语法，pwsh 的 `mkdir` 别名不接受 `-p` → 报错 → `Move-Item` 不执行 → windows 产物永不进入 release job。前文同一步骤正确用了 `New-Item`。
- 核实结论：**实锤**（纯 shell 语法错误，逻辑确定）。
- 修复：改 `New-Item -ItemType Directory -Force ../dist-artifacts | Out-Null`。

**M4. relogin 失败计数只增不减——Vision 恢复后账号永续锁死不再重登（自动重登名存实亡）**
- 位置：`backend/internal/scheduler/scheduler.go:692-728`（失败分支）、`:679-681`（计数递增）
- 详情：连续失败 5 次封顶后 `reloginFail` 恒为 5，`maybeRelogin` 每次 `wait=reloginBackoff(5)=10min`，失败分支不清计数 → 账号每 10 分钟才试一次且仍失败即保持 10min——Vision 恢复后账号永远不会自动重登，只能手动登录。
- 核实结论：**实锤**。失败分支（728 行）仅 `log.Printf`，不清 `reloginFail`。
- 修复：失败分支把 `reloginFail[acct]` 复位为 1（不是删除），保证下次尝试间隔回落到基础 30s。

**M5. 手动报名/退选后调度器状态可被下个 tick 打回（MarkDone/RemoveDone 不清理 inflight 位）**
- 位置：`backend/internal/scheduler/scheduler.go:1094`（MarkDone）、`:1130`（RemoveDone）
- 详情：`RemoveDone` 把 status 打回 pending 但不删 `inflight[acct][classID]`；若恰有一条自动链正带该 inflight 位挂着，位永不释放 → 后续手动报名永久 409；`statusIndexLocked`（822-829）无条件把非 success 置 submitted，状态机可反转。
- 核实结论：**部分实锤**（场景需要精确时序命中，概率低但确实存在；MAJOR-1 的推演与 M1 同源）。修复：`MarkDone`/`RemoveDone` 内先 `delete(s.inflight[acct], classID)` 再写状态。

**M6. `SetVision` 在 cfg.recognizer==nil 时清空现存本地引擎**
- 位置：`backend/internal/zhidao/client.go:145-152`
- 详情：`SetVision` 仅当当前引擎是 Vision 或 nil 才重建；但 runtime 热更新（handler.go:591）传 `VisionConfig{recognizer:nil}`，若当前引擎是 `LocalDdddOcrRecognizer`，第 150-151 行把整个 `visionCfg` 替换为 recognizer=nil → 引擎被清空。当前 router.go 顺序上 `SetRecognizer` 在 `SetVision` 之后侥幸覆盖恢复，但任一中间配置路径只调 SetVision 即静默清空引擎。
- 核实结论：**实锤**。修复：`cfg.recognizer == nil` 时保留 `c.visionCfg.recognizer`。

**M7. 手动报名/退选接口服务端不二次复核 can_select/满员/窗口状态**
- 位置：`backend/internal/api/handler.go:241`
- 详情：前端按钮可点性依赖 2s 轮询快照（最老 10s），名额在间隙被抢空/窗口关闭后，点击直接打平台拿 code=1 生硬文案。前端 MAJOR-1（Select.tsx:90）同源。
- 核实结论：**实锤**（体验缺陷，非安全；平台自身有最终校验，无越权风险）。修复：报名前按当前账号快照复核 `CanSelect` 与 `WindowOpened`，不通过返回友好错误。

**M8. `handleElectives?account=` 可对任意账号名触发探测——绕过调度器 30s 节流直打教务上游 + 账号枚举**
- 位置：`backend/internal/api/handler.go:192-203`
- 详情：`?account=不存在账号` → `ElectivesSnapshotFor` miss → `ProbeForAccount` → `ClientFor` miss → 回退 `ProbeNow` 直打教务 `findElectivesData`（每次消耗 idToken）。节流只在调度器 tick 内生效，API 层直通——并发可刷爆并浪费 token 配额。
- 核实结论：**实锤**。修复：`account` 参数校验在 `Registered()` 内；API 层加探测节流。

**M9. 两个管理员并发删同一账号/删与写并发——读改写无进程内串行化**
- 位置：`backend/internal/api/handler.go:682-691` + `store.SetTargetsForAccount`（先删后插）+ `Manager.clients`
- 详情：DELETE 与后续内存清理（SetTargetsForAccount nil + Accounts.Remove）无锁，并发时可将账号残留在 targets 表或 Manager.clients。SQLite 各写独立 Exec。
- 核实结论：**实锤**（影响面小，需双管理员精确并发）。修复：Store 加串行化锁或合并成事务方法。

**M10. 持 `s.mu` 时发起 SQLite 写（AppendLog/SaveSuccess）——黄金期节奏可被拖断**
- 位置：`backend/internal/scheduler/scheduler.go:860-863`、`:898-908`、MarkDone 等
- 详情：`AppendLog` 走 `db.Exec`，SQLite 单写者锁下与调度主 goroutine 竞争。窗口期极端时单条数 ms 阻塞可拖断 250ms 冲刺。
- 核实结论：**实锤**（性能风险，非正确性）。修复：拷贝状态锁外写日志，或异步日志队列。
