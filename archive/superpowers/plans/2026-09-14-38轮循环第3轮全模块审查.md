## 三、本轮新发现缺陷（按严重度分级）

### 🔴 CRITICAL

**C-1. 前端目标保存 PUT 发裸数组，后端按对象解码 100% 失败（数据链路断裂级）**
- 位置：`web/src/routes/Select.tsx:211-218`（`saveNow` 发 `body: JSON.stringify(targets)`）vs `backend/internal/api/handler.go:336-339`（`TargetsRequest{Targets []Target}`）
- 细节：`saveNow` 发裸 `[...]`，后端解码进 `TargetsRequest`（期望 `{"targets":[...]}`）→ `json: cannot unmarshal array into Go value`，`req.Targets==[]`。已用 Go 实测复现。git 历史确认 c994e43 改自动保存时删掉了 `{ targets }` 包裹，此后目标保存 100% 失败——前端 toast"目标保存失败"，刷新后 `lastJson` 为旧值不重复发送，后端目标永不更新，开窗后调度器按陈旧目标抢课。
- 修复：`body: JSON.stringify({ targets })`。

**C-2. 激活接口与会话签发未绑定"刚通过教务登录的账号"，可凭单一激活码接管任意已登录账号**
- 位置：`backend/internal/api/handler.go:150-174`（handleActivate 未认证）+ `store.go:224-245`（ConsumeActivationCode 对 account 无绑定）+ `handler.go:177-184`（issueSession）
- 细节：激活是未认证接口（router.go:106-116 仅 IP 限流），请求体 `account` 与激活码完全解耦——不要求该 account 刚通过教务登录，直接扣一次使用后签发会话。持有一个未用尽激活码（同学购码/合买）即可对任意已登录过本应用的账号名激活，拿到会话后能代报名/代退选/改目标/读日志（用户名常为学号可猜测）。
- 修复：登录返回 1001 时签发短期单次激活票据（绑定本次教务登录账号，5 分钟 TTL），`/api/activate` 必须携带票据并校验与 account 一致后才扣码发会话。

**C-3. 窗口关闭后 `releaseFullIfFreedLocked` 每 tick 清除 `isWindowClosedError` 写入的 full 标记，窗口关闭后仍 1 次/秒/链轰炸报名接口（上轮"窗口关闭防御"修复残留）**
- 位置：`scheduler.go:848`（spawnChain 每次 `releaseFullIfFreedLocked`）+ `:924-928`（isWindowClosedError → markFullLocked）+ `:1051-1068`（releaseFull 仅看快照人数，不区分"真满员"与"窗口关闭"）
- 细节：窗口关闭后 `probe` 把快照刷成空 publishes，`releaseFullIfFreedLocked` 对全空快照判"不满"→ 删除 full 标记 → spawnChain 下 tick 重新提交 → 平台返回窗口关闭错误 → 再 markFull——每 1 秒/链无限循环轰炸报名接口，窗口关闭后日志刷屏 + 打爆平台风控。
- 修复：`releaseFullIfFreedLocked` 增加"窗口已关闭/无快照数据时不解除 full"守卫——只在快照确认该课程有名额空余时才解除；或为 full 标记附窗口关闭语义。

**C-4. 调度器持 `s.mu` 发起最长 15 秒实时人数复核网络请求，黄金冲刺期锁死全调度器**
- 位置：`scheduler.go:940`（spawnChain 锁外调 `classFullRealtime`——但 `classFullRealtime` 内部的 `s.mu.Lock()` 在 `markFullLocked` 里被再次持锁）
- 细节：`classFullRealtime`（:1026-1032）调用 `client.IsClassFull`（HTTP 最长 15s）。`handleElectiveSelect`/`spawnChain` 在网络在飞期间保持 `s.mu`，整个调度器（含其它账号探测/提交/时钟对齐）被锁住最多 15 秒，黄金期 250ms 冲刺窗口被白白烧掉。
- 修复：实时复核移出锁外（先释放 `s.mu` 再网络请求，返回后重新加锁）；或将复核降级为快照判定 + 一次异步复核。

**C-5. Windows 构建步骤用 POSIX 环境变量写法跑在 pwsh 下，必挂（release 从未在 GitHub 上产过包）**
- 位置：`.github/workflows/ci.yml:90`（`CGO_ENABLED=1 go build`，`shell: pwsh`）；`.github/workflows/release.yml:46`、`:52`（同写法）
- 细节：PowerShell 无 `VAR=value cmd` 前缀语法，pwsh 把 `CGO_ENABLED=1` 当命令名，执行报 `The term 'CGO_ENABLED=1' is not recognized...`，整步失败。本地 `dist-release/xuanke-windows-amd64.exe` 是手工构建，非流水线产物。
- 修复：`$env:CGO_ENABLED='1'; go build ...` 或 step 级 `env: { CGO_ENABLED: '1' }`。

**C-6. ci-windows 恒红：没先构建前端，`//go:embed all:dist` 无文件必然编译失败**
- 位置：`.github/workflows/ci.yml:73-91`（ci-windows 只有 checkout + setup-go + go build）
- 细节：`backend/web/dist/` 在 `.gitignore:40` 被忽略、不入库（git ls-files 只有 embed.go）。runner 上 dist 不存在 → `//go:embed all:dist`（web/embed.go:11）编译报 `pattern all:dist: no matching files found`。该 job 从创建起铁定红，Windows CGO 编译验证从未真正执行过。且 windows-latest 默认无 gcc，CGO=1 还需 mingw64/tdm-gcc。
- 修复：该 job 补 npm ci + npm run build（或与 ci-pipeline 合并），并显式 setup 编译器。

### 🟠 MAJOR

**M-1. `newActivationCode` 忽略 `crypto/rand` 错误，熵源故障时产出可预测全零激活码**
- 位置：`handler.go:490-495`（`_, _ = rand.Read(b)`）
- 细节：与 `randToken`（session/store.go:129-136 已 panic）同一场景，熵源故障时激活码恒为 `XK-0000-0000-0000-0000`；且 `CreateActivationCode` 用 `INSERT OR IGNORE`，第二条起静默失败。攻击者发现两个账号拿到相同激活码即可无限激活任意账号。
- 修复：与 `randToken` 统一策略——`rand.Read` 失败即 panic（或返回错误中断批量生成）。

**M-2. `GET /api/accounts` 对任意普通会话返回全部已注册账号名单（账号枚举）**
- 位置：`handler.go:387-389`（`d.Accounts.Registered()` 全量），路由 `router.go:159-161`（仅 requireAuth）
- 细节：与"日志按账号隔离""多账号物理隔离"设计相悖。任何学生会话可枚举全部已注册账号名（学号/姓名），在 C-2 未修复前提下是高价值情报。
- 修复：非管理员会话只回显自身绑定账号（或 `[]`）；管理员会话回显全量。

**M-3. `XUANKE_ADMIN_NAME` 改名后，"会话账号=字面量 admin"与"IsAdminAccountName=配置名"错位，管理员兜底路径断言失效**
- 位置：`session/store.go:38-40`（`CreateAdmin` 硬编码 account "admin"）vs `handler.go:48-58`（`IsAdminAccountName` 用配置名）
- 细节：改名后管理员会话 `sessionAccount()` 恒为 `"admin"`，而 `handleElectives:197`、`handleState:377-381` 的兜底用 `IsAdminAccountName(acct)` 判定（配置名 "boss" 时返回 false）→ 无 `?account=` 且无目标账号时，管理员请求被当学生路径处理，`ProbeForAccount("admin")` 因无该客户端直接报错。
- 修复：`CreateAdmin` 绑定 `AdminNameValue`，或 `IsAdminAccountName` 同时判 "admin" 与配置名，杜绝两套真相。

**M-4. `handleAdminConfig` 落库失败返回 500 时，内存已改但下游热下发被跳过，报错文案与实际不符**
- 位置：`handler.go:548-613`（先 `Runtime.Update`，`SaveSettings` 失败立即 500 return，`SetVision`/`applyCaptchaRecognizerFor` 被跳过）
- 细节：管理员看到"配置已生效但落库失败"，但识别引擎/Vision 实际未同步给客户端，`GET /api/admin/config` 显示新值、识别仍走旧配置，半生效误导。
- 修复：调整顺序——先落库成功再内存生效并下发下游；或内存生效后即便落库失败也要完成下游下发并如实区分。

**M-5. 服务器无 Read/Write/Idle 超时，公网部署可被慢速请求/连接耗尽**
- 位置：`main.go:162` `http.ListenAndServe`（无任何超时）
- 细节：出站 Transport 有 15s 超时，入站无。slowloris/slow POST 可占满 goroutine 与连接池，令调度器 tick 与健康检查全部饿死。
- 修复：`http.Server{ReadHeaderTimeout: 5-10s, ReadTimeout: 15-30s, WriteTimeout: 30s, IdleTimeout: 60-120s}`。

**M-6. 登录+激活共用同一 IP 限流桶且取值仅 `RemoteAddr`，学校 NAT/反代部署下全体用户共享 5 次/分钟额度，可互相锁死**
- 位置：`router.go:86,93-116`；`clientIP` 见 `handler.go:843-849`
- 细节：登录与激活共享同一令牌桶，`clientIP` 只取 `RemoteAddr` 不解析转发头。反代/学校 NAT 后全校共用代理出口 IP → 每分钟全站仅 5 次登录+激活额度；选课当天并发登录立刻互相 429 锁死。
- 修复：登录与激活各用独立桶；评估 `X-Forwarded-For` 可信取值；或按（IP+账号）双维度限流。

**M-7. 会话令牌为无状态纯 Bearer，无绑 IP/UA、无注销接口、无定期清扫，窃取后 12h 内全权任意使用**
- 位置：`session/store.go:32-63`、`123-127`；`router.go` 无 `/api/logout`
- 细节：令牌不绑来源 IP/UA；`Session.Delete`（注销）存在但没有任何登出路由；过期清理为惰性。
- 修复：令牌绑定可选 IP 段校验或 UA；补登出接口并让前端调用；增加后台周期清扫过期会话。

**M-8. 前端 `refetchInterval` 读取先定义、自身也在轮询的 stateData，交叉驱动（stale closure 高危）**
- 位置：`web/src/routes/Select.tsx:80-85`（electives 轮询回调读 `stateData.window_opened`；stateData 来自 123 行查询且无 refetchInterval，仅 electives invalidate 时被动重取）
- 细节：开窗瞬间 electives 若因空 publishes 判 10s，stateData 永不刷新 → window_opened 恒 undefined → 停留在 10s 慢轮询错过黄金期，与 MAJOR-G 意图相悖。
- 修复：给 `/state` 查询加 `refetchInterval: 2000`，或在回调内读 `query.state.data.window_opened` 使两信号同源。

**M-9. 前端回显函数 `const initial` 与外部 `selected` 遮蔽，数据重取后回显永久失效**
- 位置：`web/src/routes/Select.tsx:128,145`（`setSelected((prev) => { ... if (Object.values(prev).some(...)) return prev; const initial = {}; ... return initial })`）
- 细节：`stateData` 第二次到达（invalidate 重取 / 10s 轮询）而目标已存在时，返回闭包里的旧 `selected`，回显失败，目标回显丢失。
- 修复：改为 `if (Object.values(prev).some((arr) => arr.length > 0)) return prev`，函数体内统一用 `prev` 构造。

**M-10. 前端 `api()` 的 `AbortController` 未接入 `RequestInit` 的 `signal`，20s 超时兜底被调用方 signal 覆盖**
- 位置：`web/src/api/client.ts:22-28`（`fetch` 的 signal 来自 `...rest` 展开，`ctrl.signal` 仅类型层面兜底）
- 修复：`fetch` 显式传 `signal: rest.signal ?? ctrl.signal`。
